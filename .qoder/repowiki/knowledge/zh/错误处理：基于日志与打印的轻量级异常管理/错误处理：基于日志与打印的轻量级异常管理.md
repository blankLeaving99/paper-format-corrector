该仓库未建立统一的错误类型体系或结构化异常机制，而是采用“日志 + 控制台打印 + sys.exit”的轻量级策略。核心特征如下：

1. **无自定义异常类**：在 `src/paper_format_corrector` 下未发现任何 `class *Error` / `class *Exception` 定义；`api/exceptions.py` 为空文件，仅占位。
2. **CLI 层以 print + sys.exit 为主**：`cli.py` 中大量使用 `print(f"错误: ...")` 配合 `sys.exit(1)` 表达参数校验失败、文件不存在、模板缺失等用户可恢复错误（如第 34-36、219-237、257-259、464-472 行）。
3. **宽泛 except Exception 兜底**：多处用 `except Exception as e:` 捕获后降级为打印警告并继续执行，例如模板样式提取失败（`infrastructure/converters/file_formatter.py` 第 54-55 行）、网络不可用时跳过更新检查（`cli.py` 第 354-359 行）、AI 生成失败回退到非流式模式（`cli.py` 第 594-603 行）。
4. **核心格式化逻辑不抛异常**：`FormatCorrector.correct_document` 内部通过子模块返回报告字典累积 `warnings`、`ref_issues`、`fig_table_issues` 等，而非抛出异常；失败路径多以 `logger.warning/error` 记录（如备份文件不存在时返回 False）。
5. **参考实现差异**：`cankao/Word-Formatter-Pro` 中的脚本使用了 `ValueError`、`FileNotFoundError`、`RuntimeError` 等标准异常，但这是被归档的参考代码，并非当前工程实际使用的错误模型。
6. **无中间件/全局异常处理器**：未发现 FastAPI/Flask 风格的异常映射、中间件或 `try/except` 顶层包装器；GUI 入口也未见 `try/except` 包裹主循环。

开发者约定（从现有模式归纳）：
- 面向用户的输入/配置错误 → `print("错误: …")` + `sys.exit(1)`。
- 可恢复的内部故障 → `logger.warning/error` 记录，函数返回默认值或空结果，由上层决定是否中断。
- 对外部依赖（网络、LibreOffice、LLM）调用 → 用 `except Exception` 捕获并降级，保证工具整体可用性。
- 避免抛出业务异常：核心 `correct_document` 始终返回报告字典，调用方自行判断成功与否。
